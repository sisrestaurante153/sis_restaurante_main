# Quick Task: Fix 3 bugs reportados pelo cliente na tela de Item

## Contexto

Cliente reportou 3 problemas na tela de edição de item (referência visual: `update/tela-item-v1.html`, screenshot do cliente anexo ao chat). Prints mostrando o bug estão implícitos — ver transcript original.

## Tarefas

### T1 — Corrigir persistência do Fornecedor 2 ao salvar

**Problema (palavras do cliente):** "ELE DISSE QUE QUANDO CLICA NO FORNECEDOR 2 PRA SALVAR NAO ESTA SALVANDO O FORNECEDOR 2, ELE MEIO QUE SOME DA TELA"

**Diagnóstico preliminar:**

Na screenshot, Fornecedor 2 aparece com:
- `Quantidade de compra = 0,0000`
- `Preço de compra = R$ 0,00`
- `Atualizado em = dd/mm/aaaa` (vazio)

`item-form-schema.ts` (linhas 17-20, 22-33) declara `purchaseQuantity` e `purchaseCost` como `positiveDecimal` (> 0), e `priceUpdatedAt` como `min(1)`. Com esses valores o zod rejeita a linha inteira. O action retorna `state.errors` com chaves aninhadas tipo `purchases.1.purchaseQuantity` que `z.flatten().fieldErrors` não expõe — o usuário vê apenas `state.message = "Revise os campos do item"` e NENHUM destaque específico, ficando com a impressão de que "sumiu".

Além disso `buildAdditionalRow` (purchases-editor.tsx linha 62-75) cria linha secundária já com `purchaseCost: "0.0000"`, que é inválido por definição — o usuário precisa obrigatoriamente editar antes de salvar, sem nenhuma indicação visual.

**Files:**
- `src/modules/catalog/server/item-form-schema.ts`
- `src/modules/catalog/ui/purchases-editor.tsx`
- `src/modules/catalog/ui/item-form.tsx`

**Action:**

1. Investigar o comportamento real clicando "Adicionar fornecedor", preenchendo com dados **válidos** (supplier + unit + quantity>0 + cost>0 + date) e clicando Salvar. Confirmar se nesse caminho Fornecedor 2 persiste (repositório re-cria todas as linhas `itemCompra` — ver catalog-repository.ts ~589). Se persistir, o bug é apenas de UX (erro silencioso) e não de persistência.
2. Tornar as mensagens de erro de fornecedores secundários visíveis:
   - No `parseItemFormData`, mapear erros de `purchases[N].campo` para chaves acessíveis pelo `getFieldError` do `item-form.tsx` (ex.: `purchases_1_purchaseCost`) OU adicionar `state.formErrors` nas mensagens top-level do `<Alert>`.
   - Em `purchases-editor.tsx`, exibir um `<Typography color="error">` dentro do bloco de cada Fornecedor secundário quando houver erros de linha aninhados.
3. Melhorar `buildAdditionalRow` para que a linha secundária entre em estado "vazio" (`purchaseQuantity: ""`, `purchaseCost: ""`) em vez de zeros enganosos, forçando o placeholder a aparecer e evitando zeros implícitos inválidos.
4. Se durante a investigação descobrir que há de fato perda de dados no caminho feliz (salvar com dados válidos), rastrear e corrigir a causa raiz (checar `readPurchasesFromFields` count mismatch entre arrays, ver se algum hidden input está ausente em algum ramo condicional).

**Verify:**
- Adicionar Fornecedor 2 com dados válidos → salvar → recarregar → Fornecedor 2 continua visível.
- Adicionar Fornecedor 2 com campo vazio/zero → salvar → mensagem de erro específica aparece, Fornecedor 2 NÃO desaparece da tela.
- Teste de integração/unidade relevante em `src/modules/catalog/**/__tests__/` ou `src/tests/` ainda passa (`pnpm test` ou equivalente).

**Done:**
- Fornecedor 2 salvo e persistido no happy path.
- Erros de validação por fornecedor têm feedback visual no bloco correto.
- `buildAdditionalRow` não cria zeros inválidos silenciosos.

`purchases-editor.tsx` linhas 327-390. No ramo `isPrimary=true` ambos campos são `<TextField select>` (linhas 337-350 e 353-368). No ramo secundário, compra é `select` mas uso é `<TextField>` readonly com `<FixadoBadge />` inline na label (linha 371-388).

A diferença visual está no label do Fornecedor 1: "Unidade de compra *" e "Unidade de uso *" são strings puras (`label="Unidade de compra"`), enquanto Fornecedor 2 tem um elemento React com badge inline na label da uso. Isso potencialmente muda a altura do label e portanto o alinhamento vertical.

Olhando a screenshot do cliente, a marcação "1 X" e "1 X" foi feita bem próxima ao **dropdown caret** — pode indicar que o cliente enxerga desalinhamento no caret, possivelmente por padding ou por o campo uso estar com `value={row.usageUnit || ""}` vazio enquanto compra está preenchido (o que pode fazer o label "float" em estados diferentes).

### T3 — Auto-cálculo do Rendimento da Porção quando Cocção Final não foi adicionada

**Problema (palavras do cliente):** "Rendimento em porções (=C7 no Excel) essa mesma função se encontra no Sistema com um parâmetros (Botão: + Adicionar Coccao Final), quando acionado é possível colocar o peso final da ficha (=C7), porem quando não aciona esse botão, o Sistema tem que fazer contas automaticamente com a soma do peso usado ou peso final (Quando tem peso limpo desconsiderar o peso usado e somar o peso limpo). Pelo teste que eu fiz no sistema, Não está atendendo pode validar!"

**Diagnóstico preliminar:**

`components-editor.tsx` linhas 324-332 (`derivedPostCookingWeight`):

```ts
const coccaoFinalStage = serializedRegularStages.find((stage) => stage.name === "Coccao / Preparo Final");
const lastCoccaoStage =
  coccaoFinalStage ??
  [...serializedRegularStages].reverse().find((stage) => stage.stageTypeCode === COCCAO_FINAL_CODE);
const derivedPostCookingWeight =
  lastCoccaoStage?.outputQuantity ||
  serializedRegularStages[serializedRegularStages.length - 1]?.outputQuantity ||
  summary?.postCookingWeight ||
  "--";
```

Hoje: se tem Cocção Final → usa ela. Senão: usa a `outputQuantity` (soma) da última stage. Senão: fallback.

O cliente quer a regra: **soma por componente** usando:
- Se o componente está em stage `limpeza_pre_preparo` → somar o `outputWeight` (peso limpo) DO COMPONENTE
- Caso contrário → somar o `outputWeight` se preenchido, senão o `quantityUsed` (peso usado)

A regra existente não aplica a exceção "peso limpo substitui peso usado" e não itera por componente — só pega o output agregado da última stage.

**Files:**
- `src/modules/engineering/ui/components-editor.tsx`
- (provavelmente) `src/modules/engineering/ui/ficha-flat-rows.ts` para expor a função utilitária
- Testes relevantes em `src/modules/engineering/ui/__tests__/` ou `src/tests/engineering/`

**Action:**

1. Localizar a fonte exata dos `rows` (ComponentEditorRow) que alimentam o cálculo — aparentemente via `regularItems` ou similar dentro de `components-editor.tsx`.
2. Implementar nova função `calculateAutoRendimento(rows: ComponentEditorRow[])`:
   ```ts
   // Para cada componente:
   //   - stageTypeCode === "limpeza_pre_preparo" → usar outputWeight (peso limpo)
   //   - senão → usar outputWeight se > 0, senão quantityUsed
   // Retornar a soma. "0" se sem componentes válidos.
   ```
3. No `derivedPostCookingWeight`, alterar a cadeia para:
   - 1º: output da stage Cocção Final (se existir explícita)
   - 2º: (NOVO) `calculateAutoRendimento(regularItems)` quando não há Cocção Final — implementa a regra do cliente
   - 3º: fallbacks existentes
4. Rodar o teste de integração: criar ficha sem cocção final, com componentes — ver que o rendimento é a soma correta.
5. Adicionar teste unitário em Jest/Vitest cobrindo:
   - Caso 1: componentes todos `limpeza_pre_preparo` → soma dos `outputWeight` (peso limpo)
   - Caso 2: componentes sem limpeza, com `quantityUsed` → soma dos `quantityUsed`
   - Caso 3: mix de limpeza + outras stages → regra por componente
   - Caso 4: cocção final presente → usa cocção final (não aplica regra nova)

**Verify:**
- Ficha sem Cocção Final, apenas componentes em stage limpeza: rendimento = soma dos pesos limpos dos componentes.
- Ficha sem Cocção Final, componentes com outras stages e peso usado: rendimento = soma dos pesos usados.
- Ficha sem Cocção Final, mix: cada componente contribui conforme sua stage.
- Ficha com Cocção Final: comportamento inalterado (continua usando o output da cocção final).
- Testes passam (`pnpm test` ou equivalente).

**Done:**
- Rendimento da Porção auto-calcula corretamente conforme regra do cliente.
- Teste unitário cobre os 4 casos.
- Verificação visual na UI.
